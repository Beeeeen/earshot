# Earshot — measured tool latency

Generated by `test/latency/latency.test.ts` on Node v22.14.0 (win32/x64).
**50 warm-up iterations discarded, then 300 measured iterations per tool** (2800 tool invocations in total). Percentiles are computed by the project's own `summarise()` in `src/protocol/timing.ts` (nearest-rank), so the arithmetic here is the same arithmetic the server uses at `GET /metrics` — though the samples are not the same samples; see the caveat at the end.

**Slowest tool at P95: `check_adherence` at 7.334 ms** — 1.5% of the 500 ms platform budget.

## What is and is not in these numbers

**Measured** — everything the server does between receiving a parsed `tools/call` and
returning a `CallToolResult`:

- the grant-table check (`canAsk`, `canReceivePrivate`)
- all data access (in-process, in-memory, synchronous by design)
- spoken-sentence construction, including `say()`'s taint scan
- routing the private half to the out-of-band channel
- `assertNoTaint` / `assertNoTaintDeep` over the outgoing object
- the disclosure-ledger write

**Not measured** — and therefore not covered by the 500 ms claim below:

- the network round trip between Alexa+ and this server
- TLS handshake, HTTP parsing, Streamable-HTTP transport framing
- OAuth bearer-token verification (`src/auth/oauth.ts`)
- JSON serialisation of the response — measured separately below
- any time the model spends deciding to call the tool, or speaking the answer

The platform documentation does not state whether its 500 ms ceiling includes the network hop. These figures are a **floor** for the round trip, and the honest claim is the one about headroom: the server-side work is 7.334 ms at worst, so 492.666 ms of the budget remains for everything this project does not control.

## Caveat: what `GET /metrics` reports is not this number

`src/server.ts` records the sample *before* calling `toCallToolResult`, so the figure it
publishes — and the one in `structuredContent.serverLatencyMs` — omits the envelope: the
taint scans, the private-channel delivery and the ledger write. The gap at P95:

| Tool | run only (P95) | full handler (P95) | omitted |
|---|---:|---:|---:|
| care_summary | 0.335 | 0.359 | 0.024 |
| check_adherence | 7.278 | 7.334 | 0.056 |
| disclosure_ledger | 2.447 | 2.481 | 0.034 |
| log_dose | 1.523 | 1.563 | 0.040 |
| next_dose | 0.150 | 0.161 | 0.011 |
| open_solo_window | 0.182 | 0.191 | 0.009 |
| report_symptom | 0.391 | 0.414 | 0.023 |
| who_can_see | 0.033 | 0.041 | 0.008 |

Both are far inside budget, so this is a reporting-accuracy issue rather than a performance one.

## Method

- `process.hrtime.bigint()` around each phase; no wall-clock arithmetic.
- A fresh household is seeded and warmed to a realistic mid-afternoon state for **every**
  iteration, outside the timed region, so mutating tools (`log_dose`, `report_symptom`) and
  ledger-reading tools (`disclosure_ledger`) see identical starting conditions each time.
- The clock is fixed at `DEMO_INSTANT`, so the data shape is identical across iterations.
- Single process, no concurrency: this measures cost per call, not throughput under load.
